# Home Assistant agent capabilities by role

**Research date:** 2026-11-05
**Question:** What capabilities would a Home Assistant manager, maintainer, or resident want from a Home Assistant agent?

## Scope and evidence

Home Assistant's official documentation does not define these three as formal product roles. For this note:

- **Manager** means the household/site owner or administrator responsible for access, configuration oversight, and the quality of the smart-home service. This most closely maps to Home Assistant's owner/administrator account, but the two are not identical concepts.
- **Maintainer** means the technically capable person who operates, configures, troubleshoots, and updates an installation. This does not assume they maintain Home Assistant Core as a project.
- **Resident** means a person who primarily uses the home and its devices. They may have a non-administrator login, or be represented as a tracked person without a login.

“Existing” below means Home Assistant has a documented capability or API that an appropriately configured integration/agent can use. It does **not** mean every installation has an AI agent configured to use it. “Potential” is a product opportunity inferred from the documented workflows, not a validated user-demand finding. The sources reviewed here are first-party Home Assistant user/developer documentation and official release posts, plus the HA MCP tool definitions available in this session on 2026-11-05; this note does not claim to represent user interviews or community consensus.

### What the available HA MCP adds

The available MCP catalog goes beyond the resident-facing Assist controls: `ha_get_overview` can summarize system/version/location, entity state, notifications and repairs, and `ha_search` can search entities and stored configurations; the descriptions explicitly warn about broad, costly reads, pagination, partial results, hidden entities, and groups whose membership must be checked. [Available HA MCP tool definitions, session snapshot (2026-11-05): `ha_get_overview`, `ha_search`]

The catalog advertises dedicated discovery/get/list paths for scenes, dashboards, automations, scripts, and helpers; the directly exposed read/write definitions in this session include automation configuration. For automation edits, the definition supports an optimistic `config_hash`, calls for best-practice guidance, and warns that `run_actions` skips triggers and conditions and that taking control of a blueprint is one-way. [Available HA MCP tool definitions, session snapshot (2026-11-05): `ha_search`, `ha_config_get_automation`, `ha_config_set_automation`, `ha_get_skill_guide`]

The MCP tool surface distinguishes read, write, and delete execution paths, while the available ESPHome device-builder tools can read or replace device YAML, validate/compile/install firmware, and manage secrets. Its definitions warn that flashing has no undo and replacing a secret is not recoverable. These are material maintainership capabilities, not ordinary household control. [Available HA MCP tool definitions, session snapshot (2026-11-05): `ha_call_read_tool`, `ha_call_write_tool`, `ha_call_delete_tool`; `esphome-device-builder__get_config`, `update_config`, `validate_config`, `compile`, `install`, `set_secret`]

This snapshot is evidence of tools exposed to this agent session, not a universal HA MCP contract or proof of backend authorization semantics. It does not establish whether a deployment uses per-user credentials, how its tool allowlist is configured, or whether MCP actions preserve HA's authenticated user context; those need deployment-specific verification.

## Short answer

The strongest role split is: a **manager** needs oversight, access governance, and safe delegation; a **maintainer** needs diagnosis and controlled system changes; a **resident** needs reliable, understandable, permission-bounded help using the home. Home Assistant already supplies substantial building blocks—entity control and conversation, automation and system APIs, account/permission controls, history/traces, backups, updates, repairs, and energy reporting. The clearest boundary is that Assist's built-in “Device control” API is limited to exposed entities and cannot do administration, while the separate “Home Assistant” LLM API can manage system resources but is administrator-only ([LLM API: The built-in APIs](https://developers.home-assistant.io/docs/core/llm/#the-built-in-apis)).

## By role

### 1. Manager / household or site administrator

**Likely job to be done:** “Tell me whether the home is healthy and under control; help me make informed changes without surprising residents or creating avoidable risk.” This is a synthesized need, not an official Home Assistant role definition.

**Existing foundation**

- **Manage people and accounts.** Home Assistant distinguishes a person (presence) from a user (login); an owner can manage accounts and only the owner can change other users' usernames/passwords. Administrators can configure integrations, devices, and system settings, and manage other users. [People and user configuration — About persons and users; About user accounts](https://www.home-assistant.io/docs/configuration/user-configuration/#about-persons-and-users).
- **Review home resources and routines.** Areas, floors, and labels organize devices/entities and can be used as automation targets; automations respond to triggers and perform actions. [Areas](https://www.home-assistant.io/docs/organizing/areas/); [Understanding automations](https://www.home-assistant.io/docs/automation/basics/).
- **Review energy use and potential savings.** The Energy dashboard summarizes electricity, gas, water, production, storage, and individual-device use, and supports using automations to shift activity to cheaper or higher-solar periods. This depends on compatible sensors and setup. [Home energy management](https://www.home-assistant.io/docs/energy/).
- **Protect and recover the installation.** On Home Assistant OS, Supervisor can make/restore backups, update Core and OS, manage apps, and check problems; Core updates automatically roll back if an update fails to start. The Supervisor is not present in every installation type. [Supervisor](https://developers.home-assistant.io/docs/supervisor/).
- **Use an administrator-only LLM API for system management.** The built-in Home Assistant API can expose tools for registries, system logs, automations, and config entries; only administrators may use it. [LLM API — The built-in APIs](https://developers.home-assistant.io/docs/core/llm/#the-built-in-apis).

**Potential agent capabilities**

1. **Plain-language home/installation briefing:** summarize unavailable or unhealthy devices, unresolved repairs, recent automation failures, upcoming updates, and backup freshness; link every finding to the relevant HA screen/log and state what is unknown. The exposed MCP overview can already return system/entity summaries, active notifications, repairs, and update-check metadata, but it does not by itself establish backup freshness or a complete cross-system diagnosis. [Available HA MCP tool definition, session snapshot (2026-11-05): `ha_get_overview`]; [System health](https://developers.home-assistant.io/docs/core/integration/system_health/); [General troubleshooting](https://www.home-assistant.io/docs/troubleshooting_general/); [Supervisor API backup information](https://developers.home-assistant.io/docs/api/supervisor/endpoints/#backup).
2. **Governed change planning:** explain the affected areas, devices, automations, and users before changing settings; ask for explicit confirmation on consequential changes; keep a clear record and describe a recovery path. The sources establish separate admin/entity permission checks and backup/restore primitives, but do not specify this proposed assistant workflow. [Permissions — Policies](https://developers.home-assistant.io/docs/auth_permissions/#policies); [Supervisor API endpoints — Backup](https://developers.home-assistant.io/docs/api/supervisor/endpoints/#backup).
3. **Household access review:** answer “who can sign in/control this?” and help an owner/admin deactivate or revoke access while preserving a person's presence record when desired. HA already separates user login from person tracking and documents deactivation/deletion; an agent must preserve that distinction. [People and user configuration — About persons and users; Deleting a user or person](https://www.home-assistant.io/docs/configuration/user-configuration/#about-persons-and-users).
4. **Energy and comfort recommendations:** identify patterns in configured energy data and propose schedules or automations for manager approval. HA provides the data/dashboard and automation primitives, but a recommendation engine that weighs comfort, cost, occupancy, and preferences is a proposed capability, not a claim about current Energy dashboard behavior. [Home energy management](https://www.home-assistant.io/docs/energy/).

**Important boundary:** do not silently give a household manager broader rights than their HA identity has. Current documented permissions apply to entity read/control/edit and admin-gated configuration; owner is an exception with full access. [Permissions — Policies](https://developers.home-assistant.io/docs/auth_permissions/#policies).

### 2. Maintainer / technical operator

**Likely job to be done:** “Help me find the cause of a failure, understand the consequences of a fix, and apply it safely.” This role is distinct from a resident's everyday use and from an upstream Core contributor.

**Existing foundation**

- **Inspect live state and events.** The authenticated WebSocket API streams state/events and accepts commands; its command context can identify the user. [WebSocket API](https://developers.home-assistant.io/docs/api/websocket/).
- **Diagnose automation behavior.** Home Assistant retains automation traces; official troubleshooting directs maintainers to traces and logs to explain conditions, failed actions, unavailable entities, and automation runs. [Troubleshooting automations](https://www.home-assistant.io/docs/automation/troubleshooting/).
- **Use repairs, logs, and health checks.** General troubleshooting directs users to System Logs and Repairs; integrations can publish system-health information such as endpoint reachability and quota. [General troubleshooting](https://www.home-assistant.io/docs/troubleshooting_general/); [Integration system health](https://developers.home-assistant.io/docs/core/integration/system_health/).
- **Validate and apply configuration.** Home Assistant documents configuration checks after file changes and automatic checks on reload/restart; most configuration can be done in the UI, but some tasks require YAML. [Configuration](https://www.home-assistant.io/docs/configuration/).
- **Back up, restore, and update (where supported).** Supervisor has endpoints for listing/creating/restoring backups and updating Core/OS/apps. These actions are privileged and installation-dependent; API availability alone is not evidence they should be automated without approval. [Supervisor API endpoints — Backup; Core update](https://developers.home-assistant.io/docs/api/supervisor/endpoints/#backup).
- **Use admin system tools through an LLM API.** The built-in Home Assistant API may expose system logs, registries, automations, and config entries; the API is admin-only. [LLM API — The built-in APIs](https://developers.home-assistant.io/docs/core/llm/#the-built-in-apis).

**Potential agent capabilities**

1. **Evidence-backed incident triage:** correlate the reported symptom with relevant entity state/history, automation traces, logs, repairs, and integration health; provide a short explanation with source evidence and confidence rather than asserting a cause prematurely. HA MCP's overview/search/config tools provide some broad discovery, but its search results may be paginated or partial and its description directs users to inspect warnings and fetch full configurations/current state separately. Cross-source correlation and confidence reporting are proposed. [Available HA MCP tool definitions, session snapshot (2026-11-05): `ha_get_overview`, `ha_search`, `ha_config_get_automation`]; existing sources below.
2. **Minimal, reviewable repairs:** suggest a specific automation/configuration change, explain its expected effect and risk, validate it, then ask before applying. The MCP automation writer supports a read/hash/transform flow and requires best-practice guidance; it also permits immediately running actions, which skips conditions and triggers. Therefore propose/diff/validate/confirm should be the default, and “run now” should be separately confirmed. [Available HA MCP tool definitions, session snapshot (2026-11-05): `ha_config_get_automation`, `ha_config_set_automation`, `ha_get_skill_guide`]; [Configuration validation](https://www.home-assistant.io/docs/configuration/); [Troubleshooting automations](https://www.home-assistant.io/docs/automation/troubleshooting/).
3. **Change and recovery assistant:** check backup status, recommend a backup before a risky update, run an approved update, monitor completion, and guide rollback/recovery if needed. Existing Supervisor operations support pieces of this, while an end-to-end agent workflow is a proposal. [Supervisor](https://developers.home-assistant.io/docs/supervisor/); [Supervisor API endpoints](https://developers.home-assistant.io/docs/api/supervisor/endpoints/).
4. **Configuration drift / broken-reference checks:** flag automations referencing missing entities/devices, mis-scoped areas, or changes that may explain a regression. HA's troubleshooting docs document these failure classes; continuous proactive auditing is a potential agent behavior. [Troubleshooting automations — entity/device references](https://www.home-assistant.io/docs/automation/troubleshooting/#my-automation-stopped-working-after-an-update).

**Maintainer guardrails:** require user identity and permissions to travel with actions. HA's developer guidance says contexts carry `user_id`, which is used for permission checks/logbook attribution; APIs and actions must check permissions, and admin-only operations should be gated. [Permissions — The context carries the user; Check a permission](https://developers.home-assistant.io/docs/auth_permissions/#the-context-carries-the-user). This makes a shared, all-powerful token a poor default for a multi-user agent. The MCP tool definitions classify operations as read/write/delete and expose some destructive or high-impact actions (including deletes, one-way blueprint conversion, firmware install, and unrecoverable secret replacement); a useful agent should separate these risk classes and obtain explicit consent before consequential writes, deletion, or device flashing. [Available HA MCP tool definitions, session snapshot (2026-11-05): `ha_call_read_tool`, `ha_call_write_tool`, `ha_call_delete_tool`, `ha_config_set_automation`, `esphome-device-builder__install`, `set_secret`].

### 3. Resident / everyday user

**Likely job to be done:** “Help me do or understand something in my home in ordinary language, with the right device and without exposing controls I shouldn't have.”

**Existing foundation**

- **Natural-language home control and queries.** Assist's conversation API accepts text and returns structured action/query/error responses; the built-in Assist API can read/control entities exposed to Assist and provides common intents. [Conversation API](https://developers.home-assistant.io/docs/intent_conversation_api/); [LLM API — The built-in APIs](https://developers.home-assistant.io/docs/core/llm/#the-built-in-apis).
- **AI for more open-ended questions/actions.** Home Assistant's official AI overview describes LLMs answering broader questions about exposed sensor information and handling requests Assist does not understand; the specific behavior depends on the selected integration/model and configured APIs. [Building the AI-powered local smart home](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/).
- **Voice and device control.** Assist supports a documented range of control intents (lights, covers/locks, media, scenes/scripts, timers, to-do lists, and others), with local and cloud pipeline choices and language/hardware tradeoffs. Capabilities vary by pipeline and integration. [Voice Chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/); [Assist pipelines](https://developers.home-assistant.io/docs/voice/pipelines/).
- **Personalized access and interface settings.** Users can have their own dashboards/profile preferences; non-admin users cannot reach configuration/system settings. Person tracking and user login are separate, so a resident need not have a login to be represented for presence automation. [People and user configuration](https://www.home-assistant.io/docs/configuration/user-configuration/).

**Potential agent capabilities**

1. **Fast everyday control with confirmation:** resolve natural-language references (“the lamp by the couch”), act only on exposed/authorized entities, confirm the actual outcome, and clearly say when a device is unavailable or ambiguous. The available catalog includes controls for lights, climate, media, vacuums, covers/locks and broadcast, in addition to live-context lookup; richer disambiguation is a proposal. Do not infer that a search match, a hidden-entity option, or a broad MCP token authorizes resident access. [Available HA MCP tool definitions, session snapshot (2026-11-05): `GetLiveContext`, `HassTurnOn`, `HassTurnOff`, `HassLightSet`, `HassClimateSetTemperature`, `HassBroadcast`, `HassVacuumStart`]; [LLM API — The built-in APIs](https://developers.home-assistant.io/docs/core/llm/#the-built-in-apis); [Conversation API — Conversation response](https://developers.home-assistant.io/docs/intent_conversation_api/#conversation-response).
2. **Home questions grounded in sensors and activity:** answer “is the door locked?”, “why did the heat turn on?”, or “what happened while I was away?” using current state, history, activity, and traces, while marking missing/out-of-date data. HA provides state/history/activity and automation traces, but an assistant that reliably combines those sources is a potential capability. [WebSocket API](https://developers.home-assistant.io/docs/api/websocket/); [Troubleshooting automations — Something turned on or off](https://www.home-assistant.io/docs/automation/troubleshooting/#something-turned-on-or-off-and-i-dont-know-why).
3. **Resident-friendly routines:** turn a stated goal (“keep the bedroom comfortable at night”) into a draft routine with schedule, devices, and exceptions explained in everyday terms; ask before enabling it. Automations are built from triggers, optional conditions, and actions, and areas can scope targets; natural-language authoring and safe approval are proposed. [Understanding automations](https://www.home-assistant.io/docs/automation/basics/); [Areas](https://www.home-assistant.io/docs/organizing/areas/).
4. **Privacy/locality choices expressed in plain language:** explain what data a voice/LLM pipeline sends externally and offer local/cloud options. HA documents multiple voice pipeline configurations, including local and cloud options; pipeline selection does not imply every model or integration has the same data handling. [Voice Chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/); [Voice Chapter 9 — local Speech-to-Phrase limits](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase).

**Important boundary:** entity permissions are not a complete role/attribute privacy system. The current developer documentation says permission policies cover entities and checks are read/control/edit; admin status separately gates configuration. A resident-facing agent should therefore use the same authenticated user context, honor exposure settings, and avoid implying that hidden entity exposure alone is equivalent to all authorization. [Permissions](https://developers.home-assistant.io/docs/auth_permissions/); [LLM API — The built-in APIs](https://developers.home-assistant.io/docs/core/llm/#the-built-in-apis). Also treat physical-security actions as a distinct class: the available intent-tool descriptions explicitly map turn-on to locking and turn-off to unlocking, so the agent must resolve the user's intended lock state and target precisely rather than rely on vague “on/off” paraphrases. [Available HA MCP tool definitions, session snapshot (2026-11-05): `HassTurnOn`, `HassTurnOff`].

## Cross-role capability priorities

| Priority | Capability | Main beneficiary | Evidence status |
|---|---|---|---|
| 1 | Permission-aware, risk-tiered action execution with clear confirmation and verified outcome | All | HA has permission/context mechanisms ([Permissions](https://developers.home-assistant.io/docs/auth_permissions/)); MCP exposes separate read/write/delete paths, but deployment identity propagation and authorization must be verified (available tool snapshot, 2026-11-05). |
| 2 | Grounded status and explanation across entities, activity, automation traces, logs, repairs, and health | Manager, maintainer, resident | MCP overview/search plus HA diagnostic sources provide pieces; integrated explanation remains potential and must expose partial/missing evidence ([overview/search tool definitions](#what-the-available-ha-mcp-adds); [automation troubleshooting](https://www.home-assistant.io/docs/automation/troubleshooting/)). |
| 3 | Draft, diff, validate, preview, and approve automations/configuration changes | Manager, maintainer; resident for simple routines | MCP supports automation reads/writes with a config hash and best-practice guidance; safe end-to-end approval remains potential ([automation tool definitions](#what-the-available-ha-mcp-adds); [configuration validation](https://www.home-assistant.io/docs/configuration/)). |
| 4 | Backup/update/recovery orchestration with explicit consent and progress | Manager, maintainer | Supervisor operations exist on supported systems; the MCP snapshot does not establish these actions are available in every deployment ([Supervisor](https://developers.home-assistant.io/docs/supervisor/); available tool snapshot, 2026-11-05). |
| 5 | Household-friendly access, privacy, energy, and routine summaries | Manager, resident | Account, energy, and automation primitives exist; recommendations/summaries are potential ([People and user configuration](https://www.home-assistant.io/docs/configuration/user-configuration/); [Energy](https://www.home-assistant.io/docs/energy/); [Automation basics](https://www.home-assistant.io/docs/automation/basics/)). |
| 6 | ESPHome device/config/firmware maintenance | Maintainer | Available device-builder tools include YAML validation, compilation and installation; firmware flashing is high consequence and not a resident need (available tool snapshot, 2026-11-05). |

**Consent and access baseline:** start in read-only mode; show the exact target and consequence before writes; request fresh confirmation for deletes, access changes, locks/unlocks, automation runs, firmware installs, backups/restores, updates, and secret replacement; preserve an attributable action record; verify results after execution; and stop if identity, scope, or target is ambiguous. These recommendations follow from HA's permission/context requirements and the MCP catalog's high-impact operations, but are proposed safeguards rather than existing guarantees. [Permissions — The context carries the user; Check a permission](https://developers.home-assistant.io/docs/auth_permissions/#the-context-carries-the-user); [Available HA MCP tool definitions, session snapshot (2026-11-05): `ha_call_read_tool`, `ha_call_write_tool`, `ha_call_delete_tool`, `HassTurnOn`, `HassTurnOff`, `ha_config_set_automation`, `esphome-device-builder__install`, `set_secret`].

## Uncertainties and limits

- The three labels are an imposed lens, not Home Assistant's published role taxonomy. “Manager” could instead mean a property/facility manager; “maintainer” could mean a Core/integration contributor. If so, the capability ranking would shift toward tenant/site boundaries or developer tools, tests, and contribution workflows.
- “Would want” is not established by these sources. The capabilities marked potential are product hypotheses derived from current documented workflows, not measured demand or a claim that users have requested them.
- Integrations, installation type, user privileges, exposed entities, language, voice hardware, and configured LLM all affect available capability. Supervisor-specific management is not universal; Assist/LLM access can be limited to explicitly exposed entities; voice command coverage varies by pipeline/language.
- The official LLM API documentation describes tools/APIs, not a universally available autonomous agent. An installation needs a conversation agent/integration and user-selected APIs. The administrator-only Home Assistant API should not be conflated with the non-admin Assist API. [LLM API](https://developers.home-assistant.io/docs/core/llm/).
- The available HA MCP tool definitions are a session-specific snapshot, not a stable public contract. The descriptions do not settle how MCP deployment-level authentication maps onto Home Assistant users/permissions, whether tool allowlists differ by user/role, what audit log covers tool calls, or which tools are enabled in an arbitrary installation. Verify those before recommending a resident-facing or multi-user deployment.
- No user research was provided. The manager/maintainer/resident split and ranking are hypotheses to validate with household owners, technical operators, and residents; property/facility managers may have tenant and site-boundary needs not captured here.
