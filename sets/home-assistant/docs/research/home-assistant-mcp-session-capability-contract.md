# Home Assistant MCP session capability contract

**Research date:** 2026-11-05
**Question:** What do the public Home Assistant MCP, HA-MCP, and ESPHome Device Builder contracts say, and how do they compare with the tools registered in this session?
**Scope:** Primary public sources owned by Home Assistant, ESPHome, and the relevant project repositories, plus read-only tool metadata only. No live Home Assistant state, configuration, entities, or secrets were inspected or changed. Home-specific entity and custom-script names are deliberately omitted.

## Findings and evidence types

Three distinct surfaces appear in this session; they should not be treated as one universal Home Assistant MCP contract:

1. **Home Assistant Assist / Device control** is a built-in LLM API in Home Assistant Core. It provides intent-style device operations and is exposed through the official MCP Server integration when selected. Assist is limited to entities exposed to Assist and is not an administrative API. [HA LLM API](https://developers.home-assistant.io/docs/core/llm/#the-built-in-apis); [official MCP Server integration](https://www.home-assistant.io/integrations/mcp_server/)
2. **HA-MCP** is a separate, explicitly unofficial project, [`homeassistant-ai/ha-mcp`](https://github.com/homeassistant-ai/ha-mcp). PyPI listed version **9.1.0**, released 2026-11-04, on the research date. Its project README advertises 87 tools; this is not the Home Assistant Core MCP integration. [PyPI release metadata](https://pypi.org/project/ha-mcp/); [project README](https://github.com/homeassistant-ai/ha-mcp/blob/master/README.md)
3. **ESPHome Device Builder** is the project in [`esphome/device-builder`](https://github.com/esphome/device-builder), with a public Device Builder API and MCP-related source under `esphome_device_builder/api/mcp/`. Its tool prefix in this session corresponds to device-builder operations, not to Core Assist or HA-MCP. [Device Builder API reference](https://github.com/esphome/device-builder/blob/main/docs/API.md); [MCP endpoint source](https://github.com/esphome/device-builder/tree/main/esphome_device_builder/api/mcp)

### Session snapshot (metadata, not execution)

The active catalog reports **103 registered definitions: 74 Assist (including home-specific scripts/intents), 21 ESPHome Device Builder, and 8 HA-MCP tool-search definitions**. The HA-MCP definitions include overview/search, automation get/set, the skill guide, tool search/call wrappers, and issue reporting. Representative registered names are `ha-mcp-server-tool-search__ha_get_overview`, `ha-mcp-server-tool-search__ha_config_set_automation`, and `esphome-device-builder__install`. The Assist custom tool names are not reproduced here.

The 8 HA-MCP definitions are a **discovery/call facade**, not evidence that only eight HA-MCP capabilities exist: the registered `ha_search_tools` metadata says it discovers tool definitions, and `ha_call_tool` accepts a tool name and arguments. Whether a particular underlying tool is enabled and callable in the connected deployment was not checked. The counts and names above are this session's metadata snapshot, not a public stable contract or a claim about a user's installation.

## Public contract compared with this session

| Area | Publicly documented capability and limit | What this session's metadata establishes |
|---|---|---|
| **Setup and profile/API choice** | Core's MCP integration can expose configured LLM APIs; its Main URL can expose all selected APIs, while Individual URLs target one API. The built-in Assist/Device control endpoint is the resident-facing, Assist-exposed-entity surface; the Home Assistant API is administrative. HA-MCP's recommended in-process setup is a custom component; setup uses an administrator token/account and offers webhook and/or network access. [Core MCP options](https://www.home-assistant.io/integrations/mcp_server/#configuration-options); [LLM API](https://developers.home-assistant.io/docs/core/llm/#the-built-in-apis); [HA-MCP in-process setup](https://github.com/homeassistant-ai/ha-mcp/blob/master/docs/in-process-server.md#setup) | Tool families are registered, but no configured API/profile, HA-MCP component version, server version, installation type, or selected account is exposed by the inspected metadata. |
| **Read-only diagnosis** | HA-MCP's public tool list includes overview/search, state, logs, history/statistics, automation traces, repairs, and integration health. Overview/search warn about broad or paginated results; partial results are not proof of no match. [HA-MCP tool list and overview](https://github.com/homeassistant-ai/ha-mcp/blob/master/README.md); [overview/search definitions](https://homeassistant-ai.github.io/ha-mcp/tools/) | `ha_get_overview` and `ha_search` are directly listed. Their metadata documents projections, filters, pagination/partial-result warnings, and broad-read costs. History, logs, traces, and system-health tools are not directly named in the 8-entry slice; discovery/call metadata could route to them, but their current availability was not tested. |
| **Everyday entity control** | Core Assist provides intent and integration tools only for entities exposed to Assist; it is not for administration. HA-MCP separately advertises broader service and bulk control. [LLM API](https://developers.home-assistant.io/docs/core/llm/#the-built-in-apis); [HA-MCP README](https://github.com/homeassistant-ai/ha-mcp/blob/master/README.md) | The 74 Assist definitions include generic device-control intents and installation-specific custom intents/scripts. This confirms a richer-than-generic intent catalog in this session, not that every entity is authorized or exposed. No custom names are included. |
| **Automation editing** | HA-MCP has read/write automation tools. The writer supports full config, `python_transform` plus `config_hash` optimistic locking, enabled state, action execution, and blueprint take-control. HA validates writes; the source calls out that `run_actions` skips triggers and conditions, and blueprint take-control is one-way. HA-MCP documents automatic edit backups. [Automation implementation](https://github.com/homeassistant-ai/ha-mcp/blob/master/src/ha_mcp/tools/tools_config_automations.py); [tool reference](https://homeassistant-ai.github.io/ha-mcp/tools/); [README safety/features](https://github.com/homeassistant-ai/ha-mcp/blob/master/README.md) | `ha_config_get_automation` and `ha_config_set_automation` are directly registered. Metadata confirms hash-based edits, best-practice guidance, run-actions and blueprint warnings. Treat runtime enable/run as distinct from editing, and require a separate confirmation before running actions. |
| **Backups and updates** | HA-MCP advertises backup/restore and update-management tools. Supervisor APIs cover backup, Core/OS/app updates, and jobs where Supervisor is present; Supervisor-backed features are not universal across HA installation types. [HA-MCP system tools](https://github.com/homeassistant-ai/ha-mcp/blob/master/README.md); [Supervisor API](https://developers.home-assistant.io/docs/api/supervisor/endpoints/); [Supervisor overview](https://developers.home-assistant.io/docs/supervisor/) | No backup/update manager is one of the 8 directly listed HA-MCP names. The generic tool-search/call path might expose such tools if they are enabled, but this is unverified. The overview metadata's HA-MCP package-update check is not an HA Core/OS backup or update operation. |
| **General HA configuration and integrations** | The public HA-MCP catalog includes helpers, scenes, scripts, dashboards, registries, integrations/config entries, areas, labels, groups, and other configuration surfaces. YAML/file editing tools are beta/opt-in and require the HA-MCP custom component's File & YAML services entry and feature flags. [HA-MCP tool list](https://github.com/homeassistant-ai/ha-mcp/blob/master/README.md); [beta features](https://github.com/homeassistant-ai/ha-mcp/blob/master/docs/beta.md) | The directly listed slice has no dedicated general integration, file, YAML, or registry writer. `ha_search_tools`/`ha_call_tool` are documented as discovery/dispatch mechanisms, not proof that a particular write tool is enabled. |
| **ESPHome** | Device Builder documents YAML read/write, component and automation editing, validation, compile/install jobs, logs, and credentials/secrets operations. Its API uses compare-before-write fields for some config edits. Install compiles and may flash; the API describes offline deferral, job tracking, and possible device recovery needs after interrupted flashing. [Device Builder API](https://github.com/esphome/device-builder/blob/main/docs/API.md); [ESPHome install guide](https://esphome.io/install/getting-started/) | 21 Device Builder definitions are registered. Metadata explicitly describes config read/replace with an `expected` precondition, validation/compile/install, and warns that flashing has no undo. A `get_config` call can target `secrets.yaml`, which would place its values in conversation context; avoid treating that as an ordinary diagnostic read. |
| **Energy and history** | HA's Energy dashboard summarizes configured electricity, gas, water, production, storage, and device data; usefulness depends on configured sources/sensors. HA-MCP's catalog includes energy-preference management and history/statistics reads. [HA Energy docs](https://www.home-assistant.io/docs/energy/); [HA-MCP tool list](https://github.com/homeassistant-ai/ha-mcp/blob/master/README.md) | No energy/history tool is directly listed among the 8 HA-MCP definitions. Search/call may make them discoverable; no data query was run. The presence of an energy dashboard in HA does not establish that its data is exposed in this session. |
| **Authentication and permissions** | HA's entity permission model relies on the request's user context and checks for read/control/edit; configuration changes are separately admin-gated. HA-MCP in-process setup runs tools with a configured administrator token; its `ha_auth` option is an admin-only access gate, not per-caller HA authorization. Other HA-MCP deployment modes have different credential models. [HA permissions](https://developers.home-assistant.io/docs/auth_permissions/); [HA-MCP in-process security](https://github.com/homeassistant-ai/ha-mcp/blob/master/docs/in-process-server.md#security); [HA-MCP threat model](https://github.com/homeassistant-ai/ha-mcp/blob/master/SECURITY.md) | Tool metadata does not disclose whether calls use Assist's exposed-entity scope, a shared HA-MCP administrator token, per-user OAuth, or another transport. Registration is not evidence of permission to a particular entity or admin capability. |
| **Allowlisting and transport** | Core MCP supports per-API URLs and options for the main URL, including administrator and read-only settings. HA-MCP supports full-catalog or tool-search exposure, per-tool enable/disable, and read/write/delete proxy separation; the in-process component can expose a conversation-agent API separately from an external MCP endpoint. [Core MCP options](https://www.home-assistant.io/integrations/mcp_server/#configuration-options); [HA-MCP discovery docs](https://github.com/homeassistant-ai/ha-mcp/blob/master/README.md#tool-discovery-for-ai-agents); [in-process exposure docs](https://github.com/homeassistant-ai/ha-mcp/blob/master/docs/in-process-server.md#exposure-modes) | The tool names indicate a search-based HA-MCP namespace plus Assist and ESPHome namespaces. The session catalog does not reveal the configured URL/transport, effective allowlist, read-only mode, policy rules, or backend identity. |
| **Audit, approvals, and sandbox** | HA-MCP documents read-only mode, per-tool approval policies, and tool usage logs, but its security policy says authenticated MCP clients are trusted principals. Its Python transform sandbox is specifically not a security boundary against adversarial clients. HA Core contexts carry user IDs for permission checks/logbook attribution; HA-MCP's in-process server records its configured server account for changes. [HA-MCP FAQ](https://github.com/homeassistant-ai/ha-mcp/blob/master/docs/FAQ.md); [HA-MCP security policy](https://github.com/homeassistant-ai/ha-mcp/blob/master/SECURITY.md); [HA permissions/context](https://developers.home-assistant.io/docs/auth_permissions/#the-context-carries-the-user); [in-process setup](https://github.com/homeassistant-ai/ha-mcp/blob/master/docs/in-process-server.md#setup) | Automation metadata includes a constrained Python-transform interface. Session metadata does not establish approval settings, log retention, a durable per-call audit trail, or whether the actual caller identity is preserved through a shared administrator credential. |

## Implications for the skill opportunity map

- Preserve **resident control**, **maintainer diagnosis**, and **administrator/system change** as separate opportunities. Assist's entity-exposure boundary is materially narrower than HA-MCP's configured-admin tool surface.
- Strong direct-session evidence supports everyday intent control, targeted overview/search, and automation review/edit guidance. Diagnosis across logs/history/traces and energy analysis are public HA-MCP capabilities, but not directly visible in the 8-tool slice; mark them as **discoverable/conditional**, pending deployment verification.
- Treat backup/restore, updates, YAML/integration changes, and ESPHome firmware installation as privileged, consequential actions. Separate draft/read/validate/compile from apply/flash; use explicit user approval and verify completion. For ESPHome, never imply a firmware flash is reversible.
- Do not present hidden/disabled tools, entity search results, Assist exposure, an MCP bearer, or a server-side admin identity as interchangeable authorization. Verify account identity, effective allowlists, transport, and read-only/policy settings before recommending a shared or resident-facing agent.
- Auditability is an unresolved deployment requirement: a tool approval feature or HA log entry is not, on current evidence, a complete actor-attributed audit trail. Ask who can review call history and what identity actions are recorded under.
- An onboarding/profile opportunity can explain the distinct APIs, setup choices, and least-privilege tradeoffs, but this research does not establish which option is active in the current installation or whether any proposed workflow is user-validated.

## Unknowns deliberately left open

The inspected metadata and public docs do not establish the connected HA Core version, installed HA-MCP/Device Builder versions, active tool settings/allowlists, user identity or role, actual transport/authentication mode, current dynamically discoverable tool availability, enabled Supervisor surface, ESPHome ingress/auth path, or audit-log retention. Resolving these would require deployment inspection; no live HA call was made for this note.
